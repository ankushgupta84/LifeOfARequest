The Life of a Request

Part I · The journey

The map

A customer in Mumbai runs PUT /vacation/photo.jpg. Four megabytes leave their laptop. This guide follows those bytes until they rest on a disk, then breaks every stop along the way so you can recognize each failure by sight.

Every performance problem you will debug comes down to one idea: a request is a traveler, and it waits in queues. A queue that drains as fast as it fills is invisible. A queue that fills faster than it drains produces latency first, then drops, then angry customers. Your job in an incident is to find which queue is full.

Linux counts almost everything. Each queue has a length you can read, a limit you can read, and a counter that ticks when the limit is hit. So debugging is rarely guesswork: you walk the path and read the counters. The hard part is knowing the path. Here it is.

How to read this guide

Check yourself

A queue never overflows, yet customers complain. How?

A queue adds latency long before it drops anything. A long block queue or a full send buffer drops nothing at all; things simply wait.

How many TCP connections does one proxied PUT involve?

Two: client to NGINX, and NGINX to a backend. Each has its own handshake, buffers, windows, and failure modes.

Why does a slow disk appear as a slow network transfer?

Backpressure. The service stops reading its socket, its receive buffer fills, the window closes, NGINX's send buffer fills, NGINX stops reading the client, and the client's upload stalls.

The photo's first packet has not left yet. Before a single byte of the PUT can travel, the laptop has to knock on our door. What happens on our side when it knocks?

Part I · Chapter 2

Knocking on the door

Three packets set up a TCP connection. On the server, those three packets move the connection through two queues. Most "connection storm" incidents are one of these two queues overflowing.

The client sends a SYN. Our kernel answers with a SYN-ACK and remembers the half-open connection. The client replies with an ACK, and the connection is established. Notice who did the work: the kernel. NGINX has not run a single instruction. The finished connection now sits on a bench, waiting for NGINX to call accept().

The two queues

The SYN queue holds half-open connections between the SYN and the final ACK. A healthy entry lives for one round trip, a few milliseconds. An entry whose ACK never comes lingers while the kernel retransmits the SYN-ACK (tcp_synack_retries, default 5, about a minute in total).

The accept queue holds finished connections that the application has not accepted. Think of a restaurant bench: the host (kernel) seats arrivals on the bench; the waiter (NGINX) takes them to tables. If the waiter is slow, the bench fills.

The bench has a size. An application passes a backlog to listen(fd, backlog), and the kernel caps it at net.core.somaxconn (4096 since kernel 5.4, 128 before). NGINX asks for 511 unless you say otherwise. So a default NGINX on a default modern kernel has a bench of 511.

When it breaks
The accept queue is full, so the kernel ignores the final ACK and drops fresh SYNs. The client sees nothing wrong, waits, and retransmits its SYN after 1 second, then 2 more, then 4 more. The signature in a latency histogram is unmistakable: spikes at about 1s, 3s, and 7s on connect time, while requests on existing connections stay fast.
Proof
ss -ltn
# State  Recv-Q Send-Q Local Address:Port
# LISTEN 511    511          0.0.0.0:443     ← bench is full
#        ^now   ^limit
nstat -az TcpExtListenOverflows TcpExtListenDrops
# run it twice a few seconds apart; a rising number is the proof
Knob
listen 443 backlog=4096; in NGINX, and net.core.somaxconn at least as large. A bigger bench absorbs bursts. It does not fix a waiter who is permanently too slow: if NGINX cannot accept as fast as connections arrive, find out why (Inside NGINX).

SYN cookies

When the SYN queue is full, the kernel has a trick. Instead of storing the half-open connection, it encodes the essentials into the sequence number of the SYN-ACK, a SYN cookie, and stores nothing. If a valid ACK comes back, the kernel rebuilds the connection from the number. An attacker who floods SYNs from fake addresses fills no memory. net.ipv4.tcp_syncookies=1 (the default) turns this on only when the queue overflows.

On current kernels the SYN queue limit is effectively the same backlog number as the accept queue. tcp_max_syn_backlog matters mainly when cookies are off.

Try it

Three things to try. Set the accept rate below the arrival rate and watch the accept queue fill, then overflow. Shrink the backlog and send a burst. Then bring the accept rate back above arrivals and notice how long recovery takes: retries keep arriving on top of new traffic.

Check yourself

ss -ltn shows Recv-Q 0 on port 443, yet ListenOverflows climbed during the night. Contradiction?

No. Recv-Q is a snapshot; the counter is a history. A burst overflowed the queue and drained. Counters catch what snapshots miss.

A customer reports that 2% of requests take exactly one second longer. First suspect?

A dropped SYN and its 1-second retransmit. Check ListenOverflows and packet drops lower in the stack.

Who performs the handshake when NGINX is frozen?

The kernel, until the accept queue fills. Clients connect successfully and then hang, which is why a frozen process looks "up" to a TCP health check.

We said "the kernel receives the SYN" as if packets teleport from the wire into TCP. They do not. Between the cable and the SYN queue lies a climb with several ledges where a packet can fall off.

Part I · Chapter 3

Through the kernel

A packet climbs from the wire to a socket in about a dozen microseconds. Along the way are four ledges where it can be dropped, each with its own counter. Learn the ledges and you can prove "the box dropped it" or "the box never saw it".

The climb

1. The ring. The NIC copies each arriving packet into a slot of a fixed-size ring buffer in RAM and raises an interrupt. If the kernel does not empty the ring fast enough, the card drops the next packet, and TCP never learns it existed.

2. NAPI and softirq. Handling one interrupt per packet would melt the CPU at high rates. So the interrupt handler does almost nothing: it switches the card to polling and schedules a softirq. The softirq (NET_RX) drains the ring in batches. It works under a budget (net.core.netdev_budget, 300 packets per pass). When it runs out of budget with packets still waiting, that is a time squeeze. Sustained squeezing means the CPU cannot keep up with the wire. Under heavy load this work moves to the ksoftirqd/N kernel threads, which you can see in top.

3. Spreading the load. One CPU core can process roughly a million small packets per second. RSS lets the card hash each connection to one of several rings, each with its own interrupt and core. If one core sits at 100% in %soft while the others idle, RSS is misconfigured or one flow dominates.

4. GRO. GRO glues consecutive segments of one connection into a single large packet before the stack sees them. One 64 KB packet costs far less CPU than 45 small ones. On transmit, TSO does the reverse. This is why tcpdump on a server shows impossible 20 KB "packets": you are looking above the merge.

5. Netfilter and conntrack. If firewall rules or NAT are loaded, conntrack keeps a table entry per connection. The table has a fixed size. When it fills, new connections are dropped, and the kernel log says so in plain words.

6. TCP. The segment is matched to a socket by its 4-tuple and placed on that socket's receive queue. The application's next recv() copies it out.

On the way out the path is shorter: socket send buffer, TCP, IP, the qdisc (a queue in front of the card that can shape or pace traffic), the driver's transmit ring, the wire.

When it breaks
Drops below TCP look like network loss: retransmits, shrinking congestion windows, slow transfers for everyone on the box, yet the network team finds nothing wrong on the wire.
Proof
ethtool -S eth0 | grep -iE 'drop|miss|fifo|no_buf|discard'
cat /proc/net/softnet_stat     # one row per CPU, hex: processed dropped time_squeeze …
mpstat -P ALL 1                # watch the %soft column per core
conntrack -S | head; dmesg -T | grep -i conntrack
ip -s link show eth0           # RX/TX errors and drops at a glance
Counters are cumulative since boot. Read them twice and subtract.
Knob
Larger rings (ethtool -G eth0 rx 4096), more queues and correct IRQ affinity, netdev_budget, netdev_max_backlog, a larger nf_conntrack_max or, better, no conntrack on the hot path. Each one trades memory or latency for capacity.

Check yourself

TcpRetransSegs is climbing, and ethtool -S shows rx_missed rising at the same rate. Is the network lossy?

Our own ring is overflowing. The network delivered the packets; we dropped them. Fix the ring size or the CPU that drains it.

One core shows 100% in %soft, fifteen others are idle. What do you check?

Queue count and IRQ affinity (ethtool -l, /proc/interrupts). Either all interrupts land on one core, or one giant flow hashes to one queue.

Why can a firewall rule added "just for logging" cause dropped connections weeks later?

It may load conntrack. Every connection then needs a table entry, and the table fills at peak.

The handshake is done and the path is clear. Now four megabytes have to cross an ocean. TCP will not simply send them. It will ask two questions before every burst: how much can the receiver hold, and how much can the network carry?

Part I · Chapter 4

Moving the bytes

TCP throughput is governed by whichever of three limits is smallest. When a customer says "my upload is slow", your whole task is to name the limit. Linux will tell you if you ask.

Two buffers per connection

Every socket has a send buffer and a receive buffer in the kernel. When the client's application calls write(), the bytes are copied into its send buffer and write() returns. TCP ships them later. The bytes stay in the send buffer until the peer acknowledges them, because they may need to be sent again. On our side, arriving bytes sit in the receive buffer until NGINX calls read().

This buffering decouples the application from the network. It also means write() returning says nothing about delivery.

The three limits

1. The receive window (rwnd): what the receiver can hold. Every ACK carries a number: "I have room for this many more bytes." If NGINX stops reading, our receive buffer fills, the advertised window shrinks to zero, and the client must stop. This is flow control. A zero window is the receiver saying "stop, I am full".

2. The congestion window (cwnd): what the network can carry. Nobody tells the sender the capacity of the path, so it guesses. It starts at 10 segments (about 14 KB) and doubles every round trip while ACKs keep arriving: slow start. When a packet is lost, it takes that as a sign of congestion and cuts the window. Then it grows again, cautiously. This sawtooth is congestion control. Linux's default algorithm is CUBIC, which reacts to loss. BBR is an alternative that models the path's bandwidth and round-trip time and largely ignores random loss.

3. The send buffer: what the sender has ready. If the application writes slowly, or the send buffer is too small to hold a full window of data, TCP has nothing more to send.

In each round trip the sender can have at most min(cwnd, rwnd) bytes in flight. Hence the one formula worth memorizing:

throughput ≈ min(cwnd, rwnd) / RTT

A long RTT hurts twice: each round delivers one window, and the window grows once per round. Mumbai to Virginia at 200 ms needs eight or nine round trips of slow start, about 1.7 seconds, before the windows sent add up to a 4 MB photo. And loss is punishing: on a path with loss rate p, a loss-based sender averages roughly MSS / (RTT × √p). At 200 ms and 1% loss that is under 1 Mbit/s, no matter how fat the link.

Loss and recovery

TCP learns of a loss in two ways. Fast retransmit: later packets arrive, the receiver keeps acknowledging the gap (with SACK describing what it has), and the sender resends the hole within about one round trip. Cheap. Timeout (RTO): nothing comes back at all, so the sender waits at least 200 ms, resends, and doubles the wait each time it fails again. Expensive, and the congestion window collapses to one segment. Tail losses, where the last packet of a response vanishes, used to always cost an RTO; the tail loss probe (TCPLossProbes) now usually rescues them.

Three small behaviors that cause big confusion

  • Nagle meets delayed ACK. Nagle holds back a small segment until earlier data is acknowledged; the receiver delays ACKs up to 40 ms hoping to piggyback. Together they add 40 ms stalls to small request/response exchanges. NGINX sets TCP_NODELAY on keepalive connections for this reason.
  • Slow start after idle. With tcp_slow_start_after_idle=1 (default), a connection idle for longer than its RTO forgets its congestion window. A keepalive connection to a backend that pauses for a second starts over at 10 segments. Many proxy operators set it to 0 inside a datacenter.
  • Autotuning. Buffers start small and grow on demand up to the third value of tcp_rmem and tcp_wmem. If the maximum is 4 MB and the path could use 16 MB (high bandwidth, high RTT), the buffer is your limit.

Check yourself

A download to one customer crawls. ss -ti on our side shows cwnd 480, retrans 0, rwnd_limited 96%. Whose problem?

Theirs. Their receiver advertises a small or closing window: a slow reader or a small receive buffer on the client.

Uploads from a region are slow; cwnd on our side says nothing useful. Why?

For an upload the client is the sender, and cwnd lives at the sender. On our side look at what we can see: our advertised window, RTT estimates, out-of-order arrivals (TcpExtTCPOFOQueue), and whether NGINX is reading promptly.

Why does a 100 KB object download in the same time on a 100 Mbit and a 10 Gbit link?

It finishes inside slow start. Round trips, not bandwidth, bound small transfers.

The bytes are arriving in our receive buffer. Somebody has to read them. That somebody is a single thread juggling ten thousand other connections at the same time.

Part I · Chapter 5

Inside NGINX

NGINX serves tens of thousands of connections with a handful of threads because it never waits. That design is its strength and the source of its most confusing failures.

One loop per worker

A master process reads the configuration, opens the listening sockets, and starts worker processes, usually one per CPU core. The master does no request work. Each worker runs one thread, and that thread runs one loop:

// the whole of NGINX, morally
for (;;) {
    n = epoll_wait(ep, events, max, timeout_until_next_timer);
    for (i = 0; i < n; i++) events[i].handler(...);   // never blocks
    expire_timers();
}

epoll answers the question "which of my ten thousand sockets has something for me?" The worker sleeps in epoll_wait() until the kernel has news: a new connection on the bench, bytes in a receive buffer, room in a send buffer. For each piece of news it runs a short handler that does what it can without waiting and returns. All sockets are non-blocking: a read with nothing to read returns EAGAIN at once, and the handler says "call me when there is more".

When it breaks
Anything that makes one handler slow stalls every connection on that worker. Usual suspects: a blocking disk write to a temp file or access log on a struggling disk, a CPU-heavy burst of TLS handshakes, a pathological regex, swapping. Customers see random multi-second pauses that correlate with nothing in the network.
Proof
top -H -p $(pgrep -d, -f 'nginx: worker')   # one worker at 100% CPU, or state D (waiting on disk)
strace -c -p <worker_pid>                    # 10 seconds; which syscalls eat the time?
strace -T -e trace=write,pwrite64,openat -p <worker_pid>   # per-call latency
Knob
Keep disks out of the loop: stream instead of buffering to temp files, buffer the access log (access_log … buffer=64k flush=1s), use aio threads if you must read files. Prefer ECDSA certificates and TLS session resumption to cut handshake CPU.

The cost of one request

  1. The client's handshake completes in the kernel. The worker wakes from epoll_wait, calls accept4(), and gets fd 12. One of its worker_connections slots is now taken.
  2. The worker reads from fd 12, decrypts TLS, parses the request line and headers, and picks a location and an upstream.
  3. It takes an idle connection from the upstream keepalive cache, or calls connect() to a backend: fd 13. A second connection slot is taken, and one ephemeral port.
  4. The body flows through. If buffering is on and the body outgrows the memory buffers, NGINX spools it to a temp file: fd 14, and blocking disk I/O inside the loop.
  5. The response is relayed. fd 13 returns to the keepalive cache, still open. fd 12 stays open waiting for the client's next request until keepalive_timeout.

So the arithmetic for a proxy: each active client costs two connection slots and at least two file descriptors. With worker_connections 1024 a worker serves at most about 500 clients. Set worker_rlimit_nofile to at least twice worker_connections, with headroom for temp files and logs.

The settings that matter for an S3 front end

worker_processes auto;
worker_rlimit_nofile 200000;
events { worker_connections 65536; }

upstream s3_backend {
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    keepalive 128;                    # idle upstream connections cached, per worker
}
server {
    listen 443 ssl reuseport backlog=4096;
    client_max_body_size 5g;
    location / {
        proxy_pass http://s3_backend;
        proxy_http_version 1.1;       # required for upstream keepalive…
        proxy_set_header Connection "";   # …together with this
        proxy_request_buffering off;  # stream PUT bodies to the backend
        proxy_buffering off;          # stream GET bodies to the client
    }
}

Upstream keepalive. Without it, every request opens and closes a backend connection. Each closed connection parks its port in TIME_WAIT for 60 seconds. At a few hundred requests per second toward one backend address you run out of the 28,000 default ephemeral ports and start returning 502s. Set proxy_http_version and the empty Connection header explicitly; older releases default to HTTP/1.0 upstream, which closes after every request.

Buffering, the real trade-off. With proxy_request_buffering on, NGINX reads the whole PUT body (to disk, for anything large) before contacting the backend. The backend is shielded from slow clients, and NGINX can retry another backend on failure. But a 5 GB upload is written to disk twice. With it off, bytes stream straight through and a slow client holds a backend connection for the whole upload, with no retry once the body has started. For large objects, streaming usually wins. The same logic applies to responses with proxy_buffering.

reuseport. By default all workers share one accept queue, and the kernel wakes whichever is waiting, which tends to favor busy workers unevenly. With reuseport each worker gets its own listening socket and queue, and the kernel spreads connections by hash. Fairer, but a stalled worker now has its own private bench that keeps filling.

Timeouts. client_header_timeout, client_body_timeout, send_timeout, proxy_connect_timeout, proxy_send_timeout, proxy_read_timeout: all default to 60 seconds, and all but the connect timeout measure the gap between two successive reads or writes, not the whole transfer. A client that sends one byte every 59 seconds never trips them. Remember that when we reach attacks.

Check yourself

The error log says "1024 worker_connections are not enough" while the box shows 3,000 open sockets against an fd limit of 65,536. Which limit was hit?

NGINX's own per-worker connection table, not file descriptors. They are separate limits.

p99 latency jumps for every customer on a host at once, while the backend's own latency is flat. One worker shows state D in top. Theory?

That worker is blocked on disk I/O, probably temp-file buffering or logging, and every connection it owns is frozen.

Why can enabling upstream keepalive cure 502s?

It stops burning one ephemeral port per request, so the port range no longer exhausts under TIME_WAIT.

Part I · Chapter 6

Inside the backend

An object store turns one customer request into a small crowd of internal requests. Its performance is the performance of the slowest member of the crowd it must wait for.

Your system has its own names for these parts. The shape below is common to most distributed object stores, and the failure patterns follow from the shape.

What one PUT does

  1. Front door. Authenticates the request, checks the signature, enforces per-tenant limits, and decides where the object goes.
  2. Placement. A metadata or placement service maps bucket and key to a set of storage nodes.
  3. Fan-out. The data is replicated (say three copies) or erasure coded (say four data fragments plus two parity) and written to different nodes, racks, or zones in parallel.
  4. Quorum. The front door waits for enough acknowledgments to promise durability, each of which typically includes an fsync.
  5. Commit. The index records that the key now points to the new data. Then the customer gets 200 OK.

A GET reverses it: index lookup, then read from one replica or from enough fragments to reconstruct. A LIST never touches data; it is a range scan of the index, which is why LIST storms hurt the metadata tier alone.

Four consequences of the shape

Tail latency compounds. If each storage node answers slowly 1% of the time, a request that must wait for all of 6 nodes is slow 6% of the time. A request touching 100 nodes is slow 63% of the time. The cure is to not wait for everyone: quorums, and hedged requests that ask a second node when the first is late. So when you see customer p99 degrade, look for a small number of slow nodes, not a uniformly slow fleet.

Every hop has a queue. Thread pools, connection pools, RPC queues. Each is a bench like the accept queue, mostly without a kernel counter. Your service's own metrics for queue depth and pool saturation are the equivalent of ListenOverflows. If they do not exist, that is your first action item.

Timeouts and retries multiply load. If NGINX times out at 60 s and retries, while the front door is still working on the first attempt, the backend now does the work twice. Three layers that each retry three times produce 27 attempts for one request. Timeouts must shrink as you go deeper, and retries need a budget. More in Backend trouble.

Backpressure is a feature. A healthy system under overload says no early and cheaply: 503 SlowDown at the front door costs microseconds. An unhealthy one accepts everything, queues it, and serves it after the client has given up. Backpressure through TCP windows is the last line of defense, and it is slow and invisible to the customer.

When it breaks
NGINX logs a large $upstream_header_time: the backend accepted the request and took long to produce the first response byte. For a PUT with streaming, you instead see the upload itself slow down, because the backend reads slowly and TCP pushes back.
Proof
On the backend host: the same box checks as anywhere (CPU, memory, disk), plus the service's own per-stage latency and queue metrics. On any node, ss -tin on internal connections shows which peer is slow, exactly as it does for customers.

Check yourself

Median PUT latency is flat, p99 tripled. Fleet-wide CPU is fine. Where do you look?

For one or two slow storage nodes or disks. Sort nodes by their own latency; the outlier is usually obvious.

Why can a GET storm leave PUTs unharmed while a LIST storm slows everything?

LISTs load the metadata index, which every request type consults.

The backend is overloaded. Why might raising NGINX's proxy_read_timeout make it worse?

Requests the client has abandoned keep occupying backend capacity for longer. Shed load instead.

Six storage nodes have received fragments of the photo and called write(). The call returned in microseconds. The data is not on disk yet.

Down to the disk

Between write() and the platter lies a cache and two queues. A storage service's latency is mostly decided here.

The page cache

write() copies your bytes into the page cache, marks those pages dirty, and returns. Kernel flusher threads write dirty pages to disk in the background. Reads check the cache first, so recently written or read data comes back at memory speed. This is why a box with "no free memory" is usually healthy: Linux fills idle RAM with cache and gives it back on demand.

Two thresholds govern dirty pages. Above vm.dirty_background_ratio (10% of available memory) background writeback starts. Above vm.dirty_ratio (20%) the kernel throttles the writing process itself: its write() calls start to block. A service that happily absorbed writes for minutes suddenly stalls, and nothing about the disk changed at that instant.

A storage service cannot promise durability from the page cache, so it calls fsync(), which blocks until the device confirms the data is safe. fsync latency is the floor of PUT latency. Some services bypass the cache with O_DIRECT and manage their own; then the queues below are all that is left.

The block layer

I/O requests queue in the block layer, where an I/O scheduler (mq-deadline, none, bfq) orders and merges them, then in the device's own queue. A disk has a fixed service rate. When requests arrive faster, they wait, and await (time in queue plus service) climbs while the device stays at 100% busy.

When it breaks
One slow disk: that node's requests lag, the fleet's p99 rises. Dirty throttling: periodic write stalls across a node. A failing disk often gets slow long before it reports errors, retrying internally for seconds per operation.
Proof
iostat -xz 1
# Device  r/s   w/s  r_await w_await aqu-sz %util
# sdc     12   410    2.1   184.3   75.4  100.0   ← this disk is drowning
# sdd     11   395    1.9     3.2    1.3   41.0   ← its neighbor is fine
grep -E 'Dirty|Writeback' /proc/meminfo
cat /proc/pressure/io                # share of time tasks stalled on I/O
dmesg -T | grep -iE 'I/O error|reset|timeout|medium'
biolatency-bpfcc -D 10 1             # latency histogram per disk
Compare disks with one another. On identical hardware under similar load, the outlier is the suspect. On NVMe, %util can read 100% while the device still has spare parallelism; trust await and queue size.
Knob
Lower dirty thresholds (or use dirty_bytes) to flush earlier in smaller bites. Eject slow disks quickly; a slow disk does more harm than a dead one, because a dead one stops being asked.

Check yourself

free -m shows 500 MB free of 256 GB. Is the node short of memory?

Probably not. Look at "available", which counts reclaimable page cache. Free memory is wasted memory.

PUT latency on one node shows a spike every 30 seconds or so. First theory?

Dirty-page writeback bursts or throttling. Watch Dirty in /proc/meminfo against the thresholds.

A disk has w_await 180 ms and zero errors in dmesg. Healthy?

No. It is slow, which for a quorum system is the worse failure. Compare it with its peers and consider ejecting it.

The photo is durable. A 200 OK travels back along the same road. One thing remains: both connections must end, and TCP endings leave more debris than you would guess.

Part I · Chapter 8

Saying goodbye

A TCP connection closes one direction at a time, and each side passes through named states. Counting sockets by state is one of the quickest diagnostics you have, once you know which states are normal in bulk and which are alarms.

The polite close and the rude one

The polite close is FIN, ACK, FIN, ACK. The rude one is a RST: "this connection does not exist, go away". The kernel sends a RST when a packet arrives for a port nobody listens on, when an application closes a socket with unread data in its receive buffer, when an application dies, or when a timeout aborts the connection. Firewalls and load balancers also send RSTs when their idle timers expire. To the other side every one of these reads as Connection reset by peer (errno 104).

One RST race deserves a name because you will meet it: the keepalive race. NGINX holds an idle connection to a backend. The backend's idle timeout fires and it closes. In the same instant NGINX sends a new request down that connection. The request meets a closed socket, gets a RST, and the customer gets a 502. The fix is ordering: the side that sends requests must give up idle connections first. Make NGINX's upstream keepalive_timeout shorter than the backend's idle timeout.

Proof
ss -s                                           # totals: estab, orphaned, timewait
ss -Htan | awk '{print $1}' | sort | uniq -c | sort -rn   # sockets by state
ss -tanp state close-wait                       # who is leaking?
nstat -az TcpEstabResets TcpOutRsts TcpExtTCPAbortOnData TcpExtTCPAbortOnTimeout
Knob
For TIME-WAIT pressure on outbound connections: reuse connections (keepalive) first, a wider ip_local_port_range second, tcp_tw_reuse=1 third. For CLOSE-WAIT there is no knob. Fix the code.

Check yourself

A box shows 40,000 sockets in TIME-WAIT. A colleague wants to page someone. Do you?

Not for that alone. Check whether they are on the listening side (harmless) or outbound toward one destination (port pressure).

CLOSE-WAIT on a backend process grows by 50 per minute. What ends this story?

"Too many open files", unless the leak is found first. Identify the peer addresses and the code path that handles them.

Sporadic 502s appear only on requests that follow a quiet period. Likely cause?

The keepalive race: the backend closes idle connections just as NGINX reuses them.

Part II · Reading the box

Method before tools

Under pressure, people run the commands they remember and stare at the numbers they recognize. A method stops you from debugging the wrong thing with great skill.

First, sharpen the complaint

"Slow" is not a symptom yet. Four questions turn it into one:

  1. Latency or throughput? "Each request takes long" (small objects, time to first byte) and "big transfers crawl" (megabits per second) have different causes. The first is about round trips and queues. The second is about windows and loss.
  2. Who is affected? One customer, one region, one host, one backend partition, or everyone. The scope points at the layer: one customer suggests their path or their workload; one host suggests that box; everyone suggests something shared.
  3. Since when? Line it up with deploys, config pushes, traffic changes, and hardware events.
  4. Whose clock? The customer measures from their code. You measure from your logs. The difference between the two is DNS, connection setup, TLS, the internet, and their own retries. Know which part your numbers cover (Reading NGINX's evidence).

Rates, not totals. Kernel counters count since boot. A ListenOverflows of 81,223 means nothing; 400 per second means a great deal. nstat prints the change since its last run by default (use -a for absolute totals), and sar prints per-second rates.

Network problems are often CPU, memory, or disk problems in disguise. A starved softirq drops packets. A swapping process stops reading its sockets. Learn the three vital signs well enough to rule them out fast.

Saturation is the run queue: the r column of vmstat 1 counts threads that are running or waiting for a core. More than the number of cores means threads wait. The load average is a smoothed version of that, with the twist that on Linux it also counts threads blocked on disk, so a high load with idle CPUs points at I/O.

Context switches (cs in vmstat, per process in pidstat -w) show how often the CPU changes tasks. A thread-per-request service under overload can spend more time switching than working. Container CPU limits add one more trap: a cgroup quota pauses the whole process for the rest of each 100 ms period once the quota is spent. The host looks idle and the service stutters. Check nr_throttled in the cgroup's cpu.stat.

Memory

Linux memory comes in two kinds. Anonymous memory is the process's own heap and stacks; it can be evicted only to swap. File-backed memory is the page cache; it can be dropped (if clean) or written back (if dirty) at any time. A healthy box runs with little "free" memory because the cache fills whatever is idle. The honest number is available in free -m.

When available memory runs low, the kernel reclaims: it evicts cache pages and, if swap exists, swaps anonymous pages. Reclaim itself costs CPU and stalls allocating threads. A process whose pages were swapped out pauses for a disk read each time it touches one. If reclaim fails, the OOM killer picks a process and kills it. From NGINX's side that looks like a sudden burst of connection resets and refused connections toward one backend.

Sockets use memory too. Ten thousand connections with 4 MB of buffered data each is 40 GB. Recv-Q and Send-Q

Recv-Q: bytes received and not yet read by our application. Persistently nonzero means our app is slow to read. Send-Q: bytes our app has written that the peer has not acknowledged (sent and unsent together). Here 1.3 MB waits: we have plenty to send and something downstream is limiting us. On a LISTEN socket the two columns mean something else: accept queue length and its limit.

skmem: socket memory

r receive memory in use, rb receive buffer limit, t memory of packets in flight, tb send buffer limit, w memory queued for sending, bl backlog, d drops on this socket. Here tb is 4 MB (autotuned to the maximum) with 1.3 MB queued, so the send buffer is not the limit. If rb is stuck small on an upload, receive autotuning is capped.

Congestion control algorithm

cubic, bbr, reno, dctcp. Tells you how the sender will react to loss.

Window scale

Shift counts agreed in the handshake (theirs, ours). The 16-bit window field is multiplied by 2^scale. If this field is missing, a middlebox stripped the option and the window is capped at 64 KB, which caps throughput at 64 KB per round trip. A classic cause of "slow only through that firewall".

rto: retransmission timeout, ms

How long the sender waits in silence before resending. Derived from RTT and its variance, floor 200 ms. A value in the seconds means repeated timeouts have backed it off: the path is in serious trouble or the peer is gone.

rtt: smoothed round-trip time / variance, ms

198 ms: an intercontinental path. High variance relative to the mean suggests a congested or wireless path. Compare with minrtt: if the current RTT is far above the minimum, queues along the path are filling.

mss: maximum segment size

Payload bytes per packet. 1448 is standard Ethernet with timestamps. Much smaller values mean tunnels or a low path MTU.

cwnd and ssthresh, in segments

38 segments × 1448 bytes ≈ 55 KB in flight per round trip. At 198 ms that is about 2.2 Mbit/s, which matches the send rate. A fresh connection shows cwnd:10. ssthresh present and close to cwnd means losses have already cut the window. Small cwnd plus retransmits is the fingerprint of a lossy path.

Byte counters

Lifetime totals. bytes_retrans / bytes_sent is the retransmission ratio for this connection: 1.4 MB of 48 MB, about 3%. Under 0.1% is clean, around 1% hurts, 3% cripples a loss-based sender on a long path.

unacked, retrans, lost

unacked: segments in flight now. retrans:1/969: one retransmission outstanding now, 969 in total. lost: segments currently presumed lost.

send

The rate cwnd and RTT would allow: cwnd × mss × 8 / rtt. An upper bound, not a measurement.

lastsnd, lastrcv, lastack: ms ago

When we last sent data, received data, received an ACK. Here we sent 4 ms ago and last received data a minute ago: a download in progress. Thousands of connections with large values in all three are idle; if they also never sent a full request, suspect slowloris.

pacing_rate

The rate at which the kernel spreads packets out instead of bursting them.

delivery_rate

The most recent measured rate at which the peer acknowledged data. This is the real throughput. If the line also carries the flag app_limited, the measurement was taken while the application had nothing more to send, and the path may be capable of more.

busy, rwnd_limited, sndbuf_limited

The most valuable fields in the line. busy: time the connection had data to send. rwnd_limited: share of that time stalled by the receiver's window. sndbuf_limited: share stalled by our send buffer being too small. Whatever remains was limited by cwnd, meaning the network. Here: 0.2% and 0%. The network is the limit.

notsent

Bytes in the send buffer not yet transmitted even once. Nonzero means the application is ahead of the network, so the application is not the bottleneck.

minrtt

The lowest RTT seen: the path's latency with empty queues.

snd_wnd

The receive window the peer currently advertises, in bytes. 3 MB here, far above the 55 KB cwnd, confirming the receiver is not the constraint. A value near zero with rwnd_limited high means the peer is not reading.

Limits that run out

Linux enforces a dozen ceilings that sit far above normal operation and directly in the path of a bad day. Know each one's error message, its gauge, and its knob.

The per-process limit is the one that bites. The trap is where it comes from: not from your shell's ulimit, but from whatever started the process. Under systemd that is LimitNOFILE= in the unit file, and the classic soft default is 1024. Always read the truth from /proc/PID/limits. NGINX can raise its workers' limit itself with worker_rlimit_nofile.

When a process hits the limit, accept() fails. The connection stays on the accept queue, the queue fills, and now you have ListenOverflows too. A leak of one descriptor per thousand requests takes days to surface and then takes the service down in minutes.

Ephemeral ports

An outbound connection needs a local port. The kernel picks one from net.ipv4.ip_local_port_range (32768 to 60999: 28,232 ports). The real constraint is that the 4-tuple must be unique, so the limit is 28,232 concurrent connections per destination address and port, counting those in TIME-WAIT.

The arithmetic that catches proxies: without keepalive, each request uses a port and then holds it in TIME-WAIT for 60 seconds. 28,232 / 60 ≈ 470 requests per second to one backend address before connect() fails with EADDRNOTAVAIL (99), "Cannot assign requested address".

sysctl net.ipv4.ip_local_port_range

Fixes, in order of preference: upstream keepalive; more destination addresses or more source addresses (each adds a full port range); widen the range to 1024 65535; net.ipv4.tcp_tw_reuse=1, which lets outbound connections reuse a TIME-WAIT port safely using timestamps.

Connection tracking

If netfilter connection tracking is active, each connection occupies a table entry until it closes and a timer expires. The table is sized by net.netfilter.nf_conntrack_max. When it fills:

The connection storm

Connections arrive faster than you can accept them, or pile up faster than they leave. The same graph can be an attack, a buggy client, or your own customers politely retrying you to death. Telling these apart is the hard part.

Why storms feed themselves

A brief stall, say a deploy that pauses accepts for two seconds, drops some SYNs. Those clients retry one second later, on top of normal arrivals. Clients with requests in flight time out, close, reconnect, and resend. Each reconnect costs a TCP handshake and a TLS handshake, the most CPU-expensive thing NGINX does. CPU saturates, accepts slow further, more SYNs drop. The system can stay in this state long after the trigger is gone. This is a metastable failure: the load that sustains the problem is caused by the problem.

The thundering herd is the synchronized form: a load balancer flips, a certificate rotates, or a backend restarts, and every client reconnects in the same instant.

What exactly is high?

A misbehaving client. Usually an SDK configured without connection reuse, a retry loop with no backoff, or a batch job launched with ten thousand threads. Diagnosis

The law to remember

concurrent connections = arrival rate × time each one stays

A rising connection count has exactly two possible causes: more arrivals or longer stays. The first branch of the tree is asking which one. Most "storms" inside a healthy perimeter are the second kind: something got slow, and slowness looks like a crowd.

Part III · Chapter 18

Backend trouble

A storage fleet rarely fails by going dark. It fails by getting slow in one corner, and then by the rest of the system reacting badly to that slowness.

Find the outlier first

With hundreds of nodes, the first move in almost any incident is a ranking. Sort nodes, disks, partitions, and tenants by latency and error rate, and look at the top of each list. A flat ranking means a shared cause. A spike means a culprit.

One slow disk or node
The commonest cause of p99 regressions. A gray failure: sick enough to hurt, healthy enough to pass health checks. Shows as one $upstream_addr dominating slow requests, one disk's await far above its peers, or one peer with a large Send-Q in ss on its neighbors. Eject it. Health checks should measure latency, not only liveness.
Hot key, hot partition, hot tenant
Load is rarely uniform. One customer hammering one prefix can saturate the one index partition that owns it while the fleet averages 20% CPU. Rank request rate and latency by tenant, bucket, and partition. The cure is per-tenant limits and splitting the partition, not more nodes.
Pauses
A process that stops for two seconds (garbage collection, a CPU quota throttle, memory reclaim, a blocking call on a slow disk) answers nothing, then answers everything late. From outside: latency spikes equal to the pause, its accept queue and socket Recv-Qs briefly fill, peers time out. Check GC logs, cpu.stat throttling, and /proc/pressure/* on the node.
Background work
Rebalancing, repair after a node loss, compaction, scrubbing, and deploys all compete with customer traffic for the same disks and network. An incident that "started by itself" often started with a node failure that triggered re-replication. These jobs need throttles that react to foreground latency.

Queues: where latency actually comes from

Service time is how long the work takes. Latency is service time plus waiting. Near saturation, waiting dominates: at 50% utilization a request waits about one service time on average; at 90%, nine; at 99%, ninety-nine. So a 10% rise in traffic near the limit can multiply latency tenfold, and "we were fine yesterday" is no defense.

Two rules follow. Bound every queue: an unbounded queue converts overload into unbounded latency, and serves requests whose clients have already left. Prefer shedding to queueing: reject the excess at the door, fast, with 503 SlowDown, so the requests you do accept finish on time.

Retries, the great amplifier

A retry is a bet that the failure was transient. Under overload the bet loses and adds load. Stacked layers multiply: SDK × NGINX (proxy_next_upstream) × front door × internal RPC. The defenses:

  • Timeouts that nest. Each layer's timeout should be shorter than its caller's, so that work is abandoned from the bottom up. Pass a deadline with the request and stop working when it has passed.
  • Backoff with jitter. Exponential spacing with randomness, so retries spread out instead of arriving in synchronized waves.
  • Retry budgets. Allow retries only up to a fraction of normal traffic, say 10%. In a real outage retries switch themselves off.
  • Retry at one layer. Decide which layer owns retries and disable them elsewhere. For NGINX, review proxy_next_upstream, proxy_next_upstream_tries, and proxy_next_upstream_timeout.
  • Idempotency. A retried PUT that the first attempt completed must not corrupt anything. Know which of your operations are idempotent.

When retries and timeouts sustain an overload after its trigger has gone, you are in a metastable failure. More capacity may not help. What works is cutting load below the point where the system recovers: shed hard at the front door, restore slowly.

Throttling done right

A 503 SlowDown is a product feature. Done well, it is cheap (decided before any expensive work), fair (per tenant, so one customer's burst does not starve the rest), and communicative (a Retry-After header, and a distinct metric so you can tell throttling from failure). When a customer says "I am getting 503s", your first query is whether those were your throttle doing its job or the system failing.

A backend triage order

  1. Scope: which request types, which tenants, which nodes? Rank.
  2. Recent change: deploy, config, node loss, rebalance, traffic shift.
  3. On a suspect node: the sixty-second checklist, then PSI, iostat, ss -tin toward its peers.
  4. Queues and pools in the service's metrics: which stage is backing up? The stage after the fullest queue is the bottleneck.
  5. Amplification: retry rates, timeout rates, 499s at the front.
  6. Mitigate before you understand: eject the node, shed the tenant, pause the background job, roll back. Root cause can wait an hour; customers cannot.

Check yourself

Fleet CPU is 25%. One customer's requests time out. No other complaints. Where do you look?

The partition or nodes that own that customer's keys, and that customer's own request rate. Averages hide hot spots.

After a five-minute network blip is repaired, error rates stay high for an hour. Why, and what do you do?

Retries and reconnects are sustaining the overload. Shed load at the front until queues drain, then readmit gradually.

Utilization rose from 85% to 93% and latency tripled. Is something broken?

Not necessarily. Queueing delay grows steeply near saturation. You are out of headroom.

Everything so far assumed the traffic meant well. Sometimes it does not. An attacker reads the same map you just learned and picks whichever queue is cheapest to fill.

Defense in layers

Each layer should drop what it can as cheaply as it can, so that expensive layers see only plausible traffic.

  1. Upstream of you. Anycast spreads the load across sites. Scrubbing services and provider filters absorb volumetric floods. Nothing on the host can substitute for this when the link itself is full. Know how to engage it before you need it.
  2. Kernel, before the stack. XDP programs or nftables rules drop by source prefix, protocol, or packet shape for a fraction of the cost of full processing. SYN cookies handle spoofed SYNs. Sensible sizes for the backlog, ring buffers, and (if you must have it) conntrack keep legitimate traffic alive under moderate floods.

Part IV · Reading NGINX source

Concepts you need first

NGINX's code looks strange until you accept one constraint: a worker may never wait. Nearly every odd-looking pattern in the source is a consequence of that single rule.

1. Non-blocking I/O and EAGAIN

A normal read() on a socket with no data puts the thread to sleep until data arrives. With ten thousand sockets on one thread, sleeping on one starves the rest. So NGINX marks every socket non-blocking. Now read() with nothing to read returns −1 at once with errno EAGAIN: "nothing now, try later". Likewise write() to a full send buffer writes what fits and reports how much. Throughout the source you will see this shape:

n = c->recv(c, buf, size);
if (n == NGX_AGAIN) {            /* nothing yet: arrange to be called back, and return */
    ngx_add_timer(rev, timeout);
    ngx_handle_read_event(rev, 0);
    return;
}

2. Readiness notification with epoll

"Try later" needs a "when". epoll provides it: the worker registers each socket once, then epoll_wait() returns the list of sockets that became readable or writable. NGINX uses epoll in edge-triggered mode: the kernel reports a socket once when it becomes ready, not continuously while it is ready. The consequence is a rule you will see obeyed everywhere: once told a socket is readable, keep reading until EAGAIN, or you will never be told again. The flags rev->ready and wev->ready record whether NGINX believes more can be done without asking the kernel.

3. State machines instead of stack frames

A blocking server keeps its place in the code: it is "in the middle of reading the header" because that is where its thread is parked. NGINX returns to the event loop between every step, so the stack is gone. It must store its place explicitly. It does so in two ways:

  • Handler pointers. Each event has a handler function pointer, and each request has read_event_handler and write_event_handler. Moving to the next stage means assigning the next function to the pointer. To follow the flow of a request, you follow assignments to these pointers. This is the key to reading the source.
  • Resumable parsers. The HTTP parser may receive a header in arbitrary pieces. It is a hand-written state machine (ngx_http_parse_request_line) with a state field in the request, so it can stop at any byte and resume.

4. Timers

Since nothing blocks, a timeout cannot be a blocking call with a deadline. Each event may have a timer, kept in a red-black tree ordered by expiry. The event loop asks the tree for the nearest expiry, sleeps in epoll_wait() for at most that long, then runs handlers of expired timers with ev->timedout = 1. That is the whole implementation of every *_timeout directive, and it explains why they measure the gap between two I/O events: each successful read or write re-arms the timer.

5. Zero-copy output

For plain HTTP file responses, sendfile() tells the kernel to move bytes from the page cache to a socket without copying through user space. For data in memory, writev() sends several separate buffers in one system call. NGINX represents output as a chain of buffers, some pointing at memory and some at file ranges, and picks the right system call for each run. With TLS the data must be encrypted in user space first, so sendfile does not apply unless kernel TLS is in use.

6. Processes, signals, shared memory

Workers are separate processes created by fork(). They share nothing by default, which removes most locking from the code. State that must be shared (rate-limit counters, the upstream zone, the TLS session cache) lives in explicitly created shared memory zones with a slab allocator and a mutex. The master controls workers with signals: HUP reloads (new workers start with the new configuration, old ones finish their requests and exit), QUIT shuts down gracefully, USR1 reopens logs, USR2 starts a new binary for a zero-downtime upgrade. A reload during an incident therefore leaves old workers alive as long as their connections last: look for "worker process is shutting down" in ps.

Check yourself

A module author reads one buffer on a read event and returns, leaving data in the socket. What goes wrong under edge-triggered epoll?

No new edge arrives for the data already there. The connection hangs until the peer sends more or a timer fires.

Why does a slow upload not trip client_body_timeout?

Each successful read re-arms the timer. It fires only when nothing at all arrives for the whole interval.

After a reload, ps shows twice the usual workers for an hour. Bug?

No. Old workers are draining long-lived connections. They exit when the last one closes.

With the rule of the house understood, the next obstacle is vocabulary. NGINX has its own string, its own allocator, its own buffer. A dozen types appear on every page.

Part IV · Chapter 21

The vocabulary

NGINX avoids the C standard library's idioms for strings, memory, and containers, and replaces them with its own. Learn these few and the code stops looking foreign.

Strings: ngx_str_t

typedef struct { size_t len; u_char *data; } ngx_str_t;

A length and a pointer. Not null-terminated. This lets a header value be a slice pointing into the receive buffer with no copy. It also means you must never pass .data to strlen or printf("%s"). NGINX's own format functions use %V for an ngx_str_t *. In gdb: p *s.data@s.len.

Memory: ngx_pool_t

A pool is a region allocator. ngx_palloc(pool, size) bumps a pointer; there is no matching free. When the pool is destroyed, everything allocated from it vanishes at once. Each connection has a pool (c->pool) and each request has one (r->pool), destroyed when the connection or request ends. This is why the source has almost no free() calls and almost no leaks: lifetime is tied to the request. Cleanup handlers (ngx_pool_cleanup_add) run at destruction to close files and release other resources.

The operational consequence: memory used by a request is held until the request ends. A long-lived request that allocates steadily (a streaming response through a careless module) grows until it finishes.

Buffers: ngx_buf_t and ngx_chain_t

struct ngx_buf_s {
    u_char *pos, *last;        /* unread data in memory lies between pos and last */
    off_t   file_pos, file_last;   /* or: a range of a file */
    u_char *start, *end;       /* the underlying allocation */
    ngx_file_t *file;
    unsigned temporary:1, memory:1, in_file:1, flush:1, last_buf:1, last_in_chain:1, …;
};
struct ngx_chain_s { ngx_buf_t *buf; ngx_chain_t *next; };

A buffer describes a piece of data, in memory or in a file. A chain is a linked list of buffers. All body data in NGINX moves as chains. Body filters receive a chain and pass a chain on. The flag last_buf marks the end of the response; flush asks for the data to be pushed out now. Consuming data means advancing pos. When a write would block, the unsent tail of the chain is kept in r->out and the write handler finishes it later.

Check yourself

A handler returns NGX_AGAIN. Who will call it again, and when?

The event loop, when the event it armed fires: the socket becomes ready or the timer expires.

Why is there no free() for a header value copied with ngx_pnalloc(r->pool, …)?

It dies with the request's pool.

You find the log text "upstream timed out" in one place in the source. How do you tell the connecting case from the reading case?

By log->action, set by the stage that was running: "connecting to upstream" versus "reading response header from upstream".

Part IV · Chapter 22

The skeleton

Four structures and one loop. Everything else in the source is a module that plugs into them.

The cycle

ngx_cycle_t is one generation of the running server: the parsed configuration, the listening sockets, the connection table, the open log files. A reload builds a new cycle from the new configuration and, if that succeeds, switches to it. The global ngx_cycle points at the current one.

At start-up each worker allocates three arrays of size worker_connections: connections, read events, and write events. That preallocation is why the limit is hard and why hitting it produces the "not enough" message instead of slower service.

Connections and events

struct ngx_connection_s {
    void          *data;       /* the object using this connection: an ngx_http_request_t, usually */
    ngx_event_t   *read, *write;
    ngx_socket_t   fd;
    ngx_recv_pt    recv;   ngx_send_pt send;   ngx_send_chain_pt send_chain;   /* I/O methods; swapped for TLS */
    ngx_pool_t    *pool;   ngx_log_t *log;
    struct sockaddr *sockaddr;  off_t sent;  ngx_uint_t requests;
    …
};
struct ngx_event_s {
    void              *data;        /* back-pointer to the ngx_connection_t */
    ngx_event_handler_pt handler;   /* what to run when this fires */
    unsigned  write:1, active:1, ready:1, eof:1, error:1, timedout:1, timer_set:1, …;
    ngx_rbtree_node_t  timer;
};

An ngx_connection_t wraps one socket, for a client or for an upstream alike. It always has exactly two events, read and write. The recv and send function pointers are how TLS is slotted in: for an HTTPS connection they point at ngx_ssl_recv and ngx_ssl_write, and the HTTP code above never knows.

The loop

/* src/os/unix/ngx_process_cycle.c */
ngx_worker_process_cycle() {
    for ( ;; ) {
        ngx_process_events_and_timers(cycle);    /* src/event/ngx_event.c */
        /* then: handle signals from the master (quit, reopen, terminate) */
    }
}
ngx_process_events_and_timers() {
    timer = ngx_event_find_timer();                 /* ms until the nearest timer */
    ngx_process_events(cycle, timer, flags);        /* = ngx_epoll_process_events: epoll_wait, then handlers */
    ngx_event_process_posted(&ngx_posted_accept_events);   /* accepts first */
    ngx_event_expire_timers();                      /* run timed-out handlers */
    ngx_event_process_posted(&ngx_posted_events);   /* deferred work */
}

Posted events are handlers queued to run later in the same iteration instead of immediately, which keeps call stacks shallow and ordering sane. When you see ngx_post_event(ev, &ngx_posted_events), read it as "call this handler soon, from the loop".

Modules

Everything from the HTTP core to gzip is an ngx_module_t. A module declares:

  • Commands (ngx_command_t[]): the configuration directives it understands, where each may appear, and the function that stores its value. To find what a directive does, search for its name in quotes; you will land in this table.
  • A context: for HTTP modules, an ngx_http_module_t with callbacks to create and merge configuration structs at three levels: main, srv (per server), loc (per location). Merging is how a value set in http {} is inherited by a location.
  • Lifecycle hooks: init_module, init_process, exit_process. In postconfiguration, modules register their phase handlers and filters.

Code fetches its settings with macros keyed by the module: ngx_http_get_module_loc_conf(r, ngx_http_proxy_module) returns the proxy module's struct for the location that matched request r. Per-request module state is fetched with ngx_http_get_module_ctx.

Where would you look to learn what proxy_next_upstream_tries does?

Search for the quoted directive name to find its command entry and the config field it sets, then search for uses of that field.

How does the same HTTP code run over plain TCP and TLS?

It calls c->recv and c->send, function pointers that are set to the TLS versions for HTTPS connections.

Part IV · Chapter 23

One request through the code

The same journey as chapter 5, with every stop named. Step through it once here, then again in the source with the debug log open beside you.

  1. ngx_event_accept() · src/event/ngx_event_accept.c
    The listening socket's read handler. Calls accept4() in a loop until EAGAIN, takes a free ngx_connection_t with ngx_get_connection() (the source of "worker_connections are not enough"), creates the connection pool, and calls the listener's handler.
  2. ngx_http_init_connection() · src/http/ngx_http_request.c
    Sets the read handler to ngx_http_wait_request_handler (or ngx_http_ssl_handshake for TLS) and arms the client_header_timeout timer.
  3. ngx_http_wait_request_handler()
    First bytes arrive. Allocates the header buffer, creates the ngx_http_request_t with ngx_http_create_request(), and moves the handler to the next stage.
  4. ngx_http_process_request_line() → ngx_http_process_request_headers()
    Loops: read, run the resumable parser (ngx_http_parse.c), return on NGX_AGAIN. Each known header is stored by a small handler found in a hash table. Picks the virtual server from Host.
  5. ngx_http_process_request() → ngx_http_handler() → ngx_http_core_run_phases() · ngx_http_core_module.c
    Header complete. The request now runs through the phases.
  6. The eleven phases
    POST_READ (realip) → SERVER_REWRITE → FIND_CONFIG (match the location) → REWRITE → POST_REWRITE → PREACCESS (limit_conn, limit_req) → ACCESS (allow/deny, auth) → POST_ACCESS → PRECONTENT (try_files, mirror) → CONTENT → LOG. Each phase is an array of handlers; each handler returns OK, DECLINED, AGAIN, or a status code.
  7. ngx_http_proxy_handler() · src/http/modules/ngx_http_proxy_module.c
    The content handler for a proxy_pass location. Creates r->upstream, installs its callbacks (create_request, process_header, finalize_request), then calls ngx_http_read_client_request_body(r, ngx_http_upstream_init).
  8. ngx_http_read_client_request_body() · ngx_http_request_body.c
    Reads the PUT body into buffers, spilling to a temp file if buffering is on. With proxy_request_buffering off it returns after the first part and the rest is relayed as it arrives.
  9. ngx_http_upstream_init_request() → ngx_http_upstream_connect() · ngx_http_upstream.c
    Builds the upstream request, then ngx_event_connect_peer() (src/event/ngx_event_connect.c) asks the load-balancing module for a peer via pc->get(). The keepalive module may hand back a cached connection here; otherwise a non-blocking connect() starts and the proxy_connect_timeout timer is armed. Action string: "connecting to upstream".
  10. ngx_http_upstream_send_request()
    Writes headers and body to the backend with c->send_chain. Arms proxy_send_timeout while blocked, then proxy_read_timeout while waiting for the reply. Action: "sending request to upstream".
  11. ngx_http_upstream_process_header()
    Reads the backend's response and calls the proxy module's parser (ngx_http_proxy_process_status_line, …_process_header). On error or timeout, ngx_http_upstream_next() decides whether to try another server, per proxy_next_upstream. Action: "reading response header from upstream".
  12. ngx_http_upstream_send_response()
    Sends response headers to the client through the header filter chain (ngx_http_send_header → ngx_http_top_header_filter). Then relays the body: unbuffered via ngx_http_upstream_process_non_buffered_request, or buffered via ngx_event_pipe() (src/event/ngx_event_pipe.c).
  13. ngx_http_output_filter() → body filter chain → ngx_http_write_filter() · ngx_http_write_filter_module.c
    Each body chain passes through filters (gzip, chunked, range, …) and ends at the write filter, which calls c->send_chain: ngx_linux_sendfile_chain (writev and sendfile) or the TLS equivalent. What cannot be sent stays in r->out; send_timeout is armed.
  14. ngx_http_upstream_finalize_request()
    The backend response is complete. The upstream connection is released through pc->free(), where the keepalive module may stash it for reuse.
  15. ngx_http_finalize_request() → ngx_http_finalize_connection()
    The busiest function in the HTTP core: every ending, normal or not, passes through it. Decrements the reference count; when the response is fully written, either ngx_http_set_keepalive() (wait for the next request) or ngx_http_close_request().
  16. ngx_http_free_request() → ngx_http_log_request()
    Runs the LOG phase, which writes the access log line with all those timers, then destroys the request pool. The photo's story ends with one line in a file.

Filters, in one paragraph

Output filters form two singly linked chains built at start-up, one for headers and one for body. Each filter module saves the current head (ngx_http_next_body_filter = ngx_http_top_body_filter) and installs itself as the new head. So filters run in the reverse of module registration order, and every filter ends by calling the next. When output looks wrong, the question is which filter touched it; the debug log prints each one's name as it runs.

Labs

You will remember what you break with your own hands. Each lab takes ten minutes and reproduces one failure from this guide. Run them on a scratch VM or a laptop, never on a machine that serves customers.

Compile the Java snippets with javac Name.java and run with java Name. Keep two terminals open: one to run the experiment, one to watch the kernel.

Lab 1 · Overflow an accept queue

A server that listens with a backlog of 8 (or the number you pass) and never accepts.

import java.net.*;
public class SlowAcceptor {
    public static void main(String[] a) throws Exception {
        int backlog = a.length > 0 ? Integer.parseInt(a[0]) : 8;
        try (ServerSocket s = new ServerSocket(9000, backlog)) {
            Thread.sleep(Long.MAX_VALUE);                    // never accept()
        }
    }
}

A client that opens 30 connections and times each one.

import java.net.*; import java.util.*;
public class Knock {
    public static void main(String[] a) throws Exception {
        String host = a.length > 0 ? a[0] : "127.0.0.1";
        int port = a.length > 1 ? Integer.parseInt(a[1]) : 9000;
        int n = a.length > 2 ? Integer.parseInt(a[2]) : 30;
        List<Socket> held = new ArrayList<>();
        for (int i = 0; i < n; i++) {
            long t = System.nanoTime();
            Socket s = new Socket();
            s.connect(new InetSocketAddress(host, port), 20_000);
            held.add(s);
            System.out.printf("%d connected in %d ms%n", i, (System.nanoTime() - t) / 1_000_000);
        }
        Thread.sleep(Long.MAX_VALUE);
    }
}

Watch: watch -n1 "ss -ltn 'sport = :9000'; nstat -az TcpExtListenOverflows TcpExtListenDrops". The first nine connections are instant (the kernel allows backlog + 1). After that, each connect waits through SYN retransmissions, and the overflow counters climb. You have reproduced the 1 s, 3 s, 7 s signature.

Lab 2 · Close a window

A server that accepts and never reads; a client that writes forever.

import java.net.*;
public class NeverReads {
    public static void main(String[] a) throws Exception {
        try (ServerSocket s = new ServerSocket(9001); Socket c = s.accept()) {
            Thread.sleep(Long.MAX_VALUE);
        }
    }
}
import java.io.*; import java.net.*;
public class Firehose {
    public static void main(String[] a) throws Exception {
        try (Socket s = new Socket("127.0.0.1", 9001)) {
            OutputStream o = s.getOutputStream();
            byte[] b = new byte[65536];
            for (long n = 0; ; n += b.length) { o.write(b); System.out.println(n + " bytes written"); }
        }
    }
}

Watch: ss -tinmo '( sport = :9001 or dport = :9001 )'. The byte count stops after a few megabytes: the server's receive buffer filled, its window went to zero, then the client's send buffer filled and write() blocked. On the client's socket find the large Send-Q, rwnd_limited near 100%, and the persist timer (zero-window probes). On the server's socket find Recv-Q full. This is backpressure, the mechanism behind half the diagnoses in this guide.

Lab 3 · Run out of file descriptors

java SlowAcceptor 1000 &                              # big backlog: handshakes complete without accept()
bash -c 'ulimit -n 64; exec java Knock 127.0.0.1 9000 200'

The client dies with java.net.SocketException: Too many open files well before 64 sockets, because the JVM itself holds descriptors. Before it dies, inspect /proc/<pid>/limits and ls -l /proc/<pid>/fd from the other terminal. Then install NGINX, set worker_rlimit_nofile 64; events { worker_connections 2000; }, run Knock 127.0.0.1 80 200, and read the error log.

Lab 4 · Loss and distance

netem makes an interface slow or lossy. On a scratch machine, apply it to loopback and repeat a large download from a local NGINX.

dd if=/dev/urandom of=/var/www/html/big bs=1M count=200
curl -so /dev/null -w '%{speed_download} B/s\n' http://127.0.0.1/big      # baseline
sudo tc qdisc add dev lo root netem delay 100ms                            # 200 ms RTT
curl -so /dev/null -w '%{speed_download} B/s\n' http://127.0.0.1/big
sudo tc qdisc change dev lo root netem delay 100ms loss 1%
curl -so /dev/null -w '%{speed_download} B/s\n' http://127.0.0.1/big &
watch -n1 "ss -tin '( sport = :80 )' | grep -oE 'cwnd:[0-9]+|retrans:[0-9/]+|rtt:[0-9./]+|delivery_rate [0-9a-zA-Z.]+'"
sudo tc qdisc del dev lo root                                              # clean up

Compare the three speeds with the formula from chapter 4. Then switch to BBR (sysctl -w net.ipv4.tcp_congestion_control=bbr) and repeat the lossy run.

Lab 5 · Exhaust ephemeral ports

In a network namespace, so your real settings are untouched:

sudo unshare -n bash
ip link set lo up
sysctl -w net.ipv4.ip_local_port_range="50000 50020"

Lab 6 · Hold slots with slow requests

Against your own test NGINX on localhost only, configured with events { worker_connections 64; } and one worker. The client opens connections and sends a header line every ten seconds, never finishing.

import java.io.*; import java.net.*; import java.util.*;
public class SlowHeaders {
    public static void main(String[] a) throws Exception {
        List<OutputStream> outs = new ArrayList<>();
        for (int i = 0; i < 80; i++) {
            Socket s = new Socket("127.0.0.1", 80);
            OutputStream o = s.getOutputStream();
            o.write("GET / HTTP/1.1\r\nHost: localhost\r\n".getBytes());
            outs.add(o);
        }
        for (int i = 0; ; i++) {
            Thread.sleep(10_000);
            for (OutputStream o : outs) {
                try { o.write(("X-Pad-" + i + ": 1\r\n").getBytes()); } catch (IOException e) { /* server closed it */ }
            }
        }
    }
}

Watch: curl localhost/ from another terminal hangs or is refused; the error log says "worker_connections are not enough"; stub_status shows Reading pinned at the limit. Now add client_header_timeout 5s; and limit_conn per address, reload, and run it again. You have tested your own defense.

A last word

The method never changes. Follow the request along its path. At each stop, ask what is waiting, what the limit is, and which counter proves it. Compare with a healthy peer. Mitigate first, explain second. The rest is practice, and now you know where to practice.
